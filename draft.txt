- pub/sub workflow
    - a client call PUBLISH msg ch
    - the handler handle the publish message
    - it will call redis to publish the msg to a channel
    - what redis will do that the msg will reach all the subscribed client?
        - the handler and the subscribed client are connected. the handler is now running a subscribed loop
            - it can receive message from the client and handle it differently
            - it can receive message from redis and send it to the client
        - to receive the message from redis, it must register a channel to redis
        - register a channel, it means the handler will send that channel to redis to put in the list on a topic
        - when publish command is handled, redis will retrieve the channels and send msg to all of them
        - the waiting handler will receive the msg and send directly to stream

- to race between the stream and the channel
    - the stream reading command and channel receives msg in different threads
    - when they got something, they would send that over the channel
    - another thread will receive that something in a loop and handle it with the write stream

- so we don't actually need 2 channels for that
    - the handler can send redis to store tx end
    - redis can send publish msg via that end
    - and the recv end can plump directly to handling loop. the reading stream loop will take another clone of tx to send when it has a command

- how we handle unsubscribe?
    - to identify the tx end to remove, we put it in a struct with subscription_id. and then search id to remove
    - how to close the loop?
        - the rx end will be closed because recv() is error when tx end is closed
        - but tx end is also shared by the stream reading loop
        - the stream reading loop can close by handling the command. it can handle all the command before sending response message to the write stream.
        - so we don't need to spin a new thread for stream reading loop. it can continue there. and when it hit unsubscribe, it will close all tx_end and exit the read and handling in subscribe mode and get back to normal read loop

- workflow summary
    - client send subscribe message to handler
    - handler change to subscribe mode => call it enter_subscribe_mode_loop
        - handler run a subscribe_mode_read_loop on the stream
            - it reads command from the client and handle it differently
            - it sends output message to the subscribe_mode_write_loop to send output to client
            - when it receives unsubscribe message
                - it will tell redis to remove the registered id with its tx_end
                - it will terminate and drop tx end for the write stream it is holding
                - it will exit subscribe_mode_loop and get back to read_loop and parse command normally
    - the tx end is registered with redis via a subscription id
        - redis must hold a subscription_struct that manage the id generation and the channel hashmap that store those id and tx end
    - the subscription_mode_write_loop will exit if all tx ends is dropped, ie, when subscription_read_mode exit on unsubscribe
